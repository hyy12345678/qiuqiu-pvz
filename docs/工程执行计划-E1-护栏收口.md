# 球球的植物大战僵尸 · E1 执行计划（护栏收口）

> 日期：2026-11-20
> 上游依据：[docs/项目分析-2026-11-20.md](项目分析-2026-11-20.md) §7.3 三条硬伤、§9 P0 四项。
> 本轮性质：**工具与流程收口**，不改任何游戏规则、数值与画面。`src/**` 预期零改动。
> 放行条件：`verify` 全链绿，且本轮结束时 `dist` 与 `src` 的对应关系可被自动证明。

## 1. 为什么要做这一轮

分析报告 §7.3 指出的三条问题都不是"代码写错了"，而是**执行链让护栏证明不了它声称的事情**：

| # | 现状 | 后果 |
|---|---|---|
| 1 | `verify` 顺序是 `… → test → build → parity:dist → …` | `build` 刚重写完 dist，紧接着比对它自己，属自证；提交在仓库里的陈旧 dist 永远不会被发现 |
| 2 | `--rebase` / `--update` 一条命令直接写基线 | 测试为红时也能盖章；绿只代表"和上次盖章一致" |
| 3 | 构建戳只有版本号 | 判断不了"这份 dist 是不是当前 src 构建的" |
| 4 | 无 CI | 前面三条全靠自觉执行 |

## 2. 决策记录

**D1 · `parity:dist` 前移到 `build` 之前。**
让"提交的 dist 是否对应当前 src"成为真正的门前检查。改完源码忘了重新构建时，`verify` 在 `parity:dist` 处立即红，而不是被随后的 `build` 掩盖。
*曾考虑*：保留原顺序、只加 `git diff --exit-code dist/`。否决理由：新的 dist 尚未提交时该命令必然失败，`verify` 就只能在提交后才能跑，与"提交前验收"的用法冲突。

**D2 · `dist:fresh` 独立成一条命令，只进 CI、不进 `verify`。**
`git diff --exit-code -- dist/` 回答的是"构建产物有没有一并提交"，属于提交后/CI 语义。放进 `verify` 会逼着人先提交再验收。

**D3 · 构建戳用「源码摘要」，不用 git SHA。**（对分析报告 P0-3 的**有意修正**）
原建议是加 git SHA。实际存在提交时序悖论：dist 先构建、后提交，提交之后戳里的 SHA 必然指向**父提交**，比不加更误导。
改用 `src/**` 清单摘要（与 `check-fingerprint` 同一套 `buildManifest`，sha256 后截 8 位）：
- 提交前后一致，不随 HEAD 漂移；
- 直接回答"这份 dist 是不是当前源码构建的"；
- 与 `fingerprint` 共享同一份哈希来源，不会因为两份实现漂移而对不上。

新格式：`/* build: v0.1.0 pretty · src 9f3a2c1a */`（min 形态为 `minified`）。
`check-parity --dist` 本来就整段剥离 `/* build: … */` 再比，因此不受影响；唯一需要同步的是 `tests/browser/lib.mjs` 的 `RELEASE_STAMP` 正则。

**D4 · 重盖加闸：dry-run 默认，测试先绿才盖章。**
- `node scripts/check-parity.js --rebase` 不带 `--yes`：只打印将要吸收的差异行数与逐行摘录，**不写文件**，退出码 1。
- `node scripts/check-fingerprint.js --update` 不带 `--yes`：同样只打印新增/缺失/变化清单。
- npm 脚本承担"测试先绿"：`npm test && … --yes`。想跳过测试只能手敲原命令，属于显式越权。

**D5 · CI 用 GitHub Actions，固定 Node 22 + Chromium。**
步骤与 `verify` 同构，但额外包含 `parity:dist`（构建前）与 `dist:fresh`（构建后），弥补 `verify` 为了本地可用性不能自带的两项。

## 4. 本轮明确不做

- 不动 `src/**`（`parity` 与 `fingerprint` 必须保持 PASS，不需要重盖）。
- 不删减现有护栏（那是 E2 的议题：5 条轨迹减到 2 条、fingerprint 扩范围）。
- 不拆 `updatePlay`（E3）。
- 不改游戏行为、数值、画面。

### 5.3 本轮最值得记的一点

**修护栏的这一轮，自己没有重盖任何一份基线。**

`git status` 里 `src/**` 零改动，因此：

- `parity` 3404/3404 —— 不需要 `--rebase`；
- `fingerprint` 39/39 —— 不需要 `--update`；
- `dist` 只变了 1 行（构建戳）。

这反过来证明了本轮改动的性质：**全部落在工具链与文档层，没有借「护栏收口」之名改游戏行为**。如果哪天类似的工具轮需要重盖基线，那说明它顺手改了 src，应当被质疑。

### 5.4 负向验证（证明新闸真的会拦）

| 场景 | 结果 |
|---|---|
| `node scripts/check-parity.js --rebase`（无 `--yes`） | 退出码 1，打印将吸收的差异，文件字节不变 |
| `node scripts/check-fingerprint.js --update`（无 `--yes`） | 退出码 1，同上 |
| `npm run dist:fresh`（dist 已改未提交） | 退出码 1，打印 `-/* build: … */` / `+/* build: … · src … */` 的真实差异 |
| 旧格式戳 `/* build: v0.1.0 pretty */` | 浏览器套件 REJECT（「不是发布构建」） |
| `/* dev build */` | REJECT（「缺少发布构建戳」） |
| 非法摘要 `· src zzzzzzzz` | REJECT |

### 5.5 遗留与下一轮

- **`dist:fresh` 在提交前必然红**，这是设计而非缺陷；提交后应变为绿。CI 里它排在 `build` 之后，语义与本地一致。
- 本轮未处理 E2（护栏减负：5 条轨迹 → 2 条、fingerprint 扩到 `scripts/ + tests/`）与 E3（拆 `updatePlay`）。
- `parity:legacy` 仍是预期非绿；本轮只在 `check-parity.js` 里修正了那句会误导人的「⇒ 产物 ≡ legacy」注释，行为未动。
