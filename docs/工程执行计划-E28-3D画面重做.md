# E28：3D 画面重做

> 起因：球球觉得原来的美术太简单，想要更精致、更有冲击力的画面，并且可以做成 3D。
> 决策：用 three.js 重做战场与角色，**不保留 2D 战场兜底**（作者确认）。
> 这一轮推翻了[决策记录-画风取舍](决策记录-画风取舍.md)里「只做细节密度、不做风格迁移」的结论：
> 那份记录的前提是 2D 程序绘制的像素量（一株向日葵约 50px）承载不了更高的画风；换成真 3D 之后，
> 体积、光照、阴影、泛光都由渲染器给出，这个前提不成立了。

## 1. 架构

```
core/（不变） ──读──> render/scene3d/world-view.js ──> three.js 场景树
                                   │
              renderer.js：WebGL 画到离屏画布 → 泛光 → 输出
                                   │
render/scenes/index.js：ctx.drawImage(3D 画布) → 2D 界面层（scenes/*、hud.js、skin.js）→ 暗角
```

- **核心层一行没改**。规则、随机流、关卡、存档、规则测试全部原样。
- **3D 画到离屏画布，再整幅贴进 2D 主画布**。界面（文字、按钮、卡片）在 2D 里画最清楚；输入、热点、DPR、
  测试夹具都已按 2D 主画布组织。同一个任务里 render → drawImage，不需要 `preserveDrawingBuffer`。
- **世界视图只读**。上一帧血量、光线起点、粒子归属的行都存在视图自己的 Map / WeakMap 里，
  `tests/render-readonly.test.mjs` 用快照比对守住。
- **渲染层自己的特效用自己的随机源**（`fx.js` 的 `mulberry32(0xC0FFEE)`），不碰 `world.rng / world.fxRng`。

## 2. 美术做法

| 部分 | 做法 |
|---|---|
| 角色 | 基础几何体拼装（球、胶囊、车削、管、挤出叶片），按「骨骼节点 × 材质类」合并，一个角色 3–6 次绘制调用；节点独立做动画 |
| 材质 | 顶点色给固有色；哑光 / 釉面（清漆）/ 金属 / 自发光 / 半透明五类；全场共用一圈菲涅尔轮廓光，把角色从草地上剥出来 |
| 环境 | 棋盘草皮 + 3400 根实例化草叶（顶点着色器里随风摆）、房子与门廊、栅栏树篱、人行道街道路灯、前景花坛；贴图全部由 2D canvas 现场画 |
| 光 | 半球光 + 投影日光 + 补光 + 4 盏固定点光源池（数量固定，避免着色器重编译）；夜里换月光、雾、星空、萤火虫、亮窗与路灯光柱 |
| 后期 | HalfFloat + 4×MSAA → UnrealBloom（阈值 1.0，只有自发光件会泛光）→ Neutral 色调映射 |
| 冲击力 | 受击闪白、铁门火花、护具分档变形并在打穿时飞出残骸、掉胳膊、爆炸火团 + 冲击环 + 焦痕 + 动态光、被炸死成焦炭、镜头震动、开场从街道摇回草坪、失败时推近到冲进屋子的僵尸 |
| 界面 | 深色琉璃面板 + 金边、糖果按钮（带侧壁与扫光）、挤出立体标题；卡片与图鉴肖像是 3D 模型启动时渲染出来的 |

## 3. 拾取

透视下草坪不再是规整网格。`picking.js` 从逻辑坐标发射线：**先打植物**（点在植物头上也算点中它的格子），
再打地面；阳光按屏幕距离（46px）取最近一颗，把它的逻辑坐标交给核心层 `collectSun`。
`game.js` / `ui/input.js` 通过注入的 `picker` 使用它；不注入时退回逻辑网格（测试、无 WebGL），行为与之前一致。

## 4. 性能与画质分档

- 有 GPU 的机器（本机 M 系列 Mac，Chromium + Metal）：满配 60fps。
- 软件光栅（CI 的 SwiftShader）：全特效约 5fps。实测瓶颈依次是草叶实例（约 60ms/帧）和整体几何量，与材质类型关系不大。
  识别到软件光栅就直接用低配：关泛光与 MSAA、阴影贴图 1024、草叶只留 850 根、0.65 倍分辨率起步，约 11–15fps，够跑完浏览器测试。
- 运行中 90 帧平均超过 26ms 就降一档分辨率（2 → 1.5 → 1.25 → 1 → 0.8 → 0.65），只降不升。
- `?gfx=low|high` 手动指定。

## 5. 护栏怎么跟着改

| 原护栏 | 现在 |
|---|---|
| 2 条 2D 背景绘制轨迹（白天 / 夜间） | `render-background-trace`：3D 环境结构基线（每个网格的几何、材质类、投影开关、灯光参数，昼夜各一份） |
| 背景离屏缓存测试 | `render-background`：昼夜主题切换、同主题空操作、点光源池固定 4 盏、布景材质都已绑定 |
| 植物绘制表 ↔ 数值表 | `render-plant-table`：3D 模型表 ↔ 数值表（植物与僵尸），每个模型都建得出网格且绘制调用不失控 |
| 绘制只读 | `render-readonly`：世界视图同步多帧、昼夜、暂停、结算都不改 world |
| — | 新增 `render-picking`：45 格中心全覆盖、点植物头部、草坪外不拾取、阳光拾取、点击结算顺序 |
| 场景测试的 2D 断言 | 场景夹具默认挂真实世界视图（`tests/helpers/view3d.mjs`，只是不调 WebGL），断言改为 3D 模式切换、模型姿态分叉、弹丸原型配色 |
| 浏览器 3 条绘制轨迹 | 仍然逐行锁 2D 主画布的全部调用（即界面层），3D 战场在轨迹里是一次整幅 drawImage；另加画面统计：菜单有蓝天、白天草坪偏绿且亮、夜战明显压暗 |
| 发布冒烟的「格子像素变了」 | 草会摇，整格像素每帧都变，原断言失去意义。改成「阳光数字区域（静止）变了」+「目标格红色分量上升（长出黄色向日葵）」；用「种到别的格子」做过反例，确认会红 |

数字：单测 209 → 214 条（共 218 条声明，测试清单下限 213 → 218），浏览器 6 条全绿，`npm run verify` 全绿。

## 6. 代价与已知局限

- **体积**：产物 192 KB → 1.6 MB（pretty），其中 three.js 约 1.25 MB；min 版约 0.74 MB。仍是单文件、完全离线。
- **需要 WebGL2**。不支持时界面照常，战场位置显示提示。
- **CI 跑的是低配画面**。浏览器测试证明「能启动、能交互、画出来了」，不证明满配画面的观感；观感只能人看。
- **未实测**：真机触屏（iPad / 安卓）上的帧率与发热、Safari 与 Firefox。
- 已修：铁门僵尸的首见提示（`core/sim.js`）原写「豌豆打不动，换火豌豆或炸弹」，与规则不符（E23 起弹道削到 1/4 而非无效，火豌豆直击同样被削）。
  改为「铁门僵尸来了！豌豆伤害只剩 1/4，快用炸弹！」，并由 `tests/zombie-screen.test.mjs` 把提示文字与 `SCREEN_BALLISTIC_MULT` 绑在一起。

## 7. CI 首次实跑（追记）

第一次推送后 CI 红在 `test:browser:baselines`：两条战斗轨迹各超时 120 秒。原因是到达战斗画面要逐 16.7ms 推进约 600 帧，
3D 版每帧都真渲染，ubuntu 上的软件光栅比本机慢约 3 倍。修法：「到达」路上改成每帧 50ms（游戏单帧 dt 上限）推进，
帧数降到约三分之一；被记录的那一帧仍是标准 16.7ms。到达过程的时间步长变了，战斗两条轨迹因此重新盖章（行数不变，
卡片冷却等随时间变化的数值不同），超时放宽到 360 秒。
