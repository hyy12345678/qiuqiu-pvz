# 球球的植物大战僵尸 · E3 执行计划（模拟层拆分）

> 日期：2026-11-20
> 上游依据：[docs/项目分析-2026-11-20.md](项目分析-2026-11-20.md) §5.2 第一条技术债、§9 P1-5。
> 本轮性质：**纯结构重构**。不改任何规则、数值、绘制与输入行为。
> 放行条件：`npm test` 与 5 条绘制轨迹**在测试文件一字未改的前提下**全绿。

## 1. 问题

[src/core/sim.js](../src/core/sim.js) 的 `updatePlay` 是全项目最大的函数：**343 行**，一个函数里顺序做完八件事
（出怪、植物、弹丸、僵尸、小推车、阳光、表现、结算）。后果：

- 改任何一条规则都要进同一个函数，review 时看不出改的是哪一段；
- 唯一的中断语义（判负后 `return`）藏在第 270 行，改动时极易被后续步骤破坏；
- 117 个函数里有 11 个超 80 行，最大的三个都在这里和渲染层。

## 2. 决策记录

**D1 · 拆函数，不拆文件。**
`sim.js` 保持单文件 390 行。八个 `step*` 共享同一批 import 与同一个 `world`，拆成八个文件只会制造八个 import 头。
按"职责段"拆，不按"行数"拆——这与项目 v0.2 方案 §1 原则 3「按依赖方向拆分，而不是按文件长度拆分」一致。

**D2 · 顺序即语义，禁止重排。**
`updatePlay` 只做编排，调用顺序与原函数段落顺序**逐段对应**。理由：每个 `step` 都会消耗 `world.rng` / `world.fxRng`，
调换任意两步都会改变随机数消耗次序，进而改变整局结果。这条写进了函数头注释。

**D3 · 判负用返回值表达，不用异常、不用标志位。**
原实现在僵尸段之后 `return;` 直接结束本帧。拆分后 `stepZombies` 返回 `true`，编排处 `if(stepZombies(world, dt)) return;`。
异常会打乱 `ports.sound` 的调用时序；全局标志位会让"本帧已结束"变成一个跨函数的隐式状态。

**D4 · 不改任何一行业务代码，只改函数边界。**
拆完后逐行核对 `parity` 差异，确认**没有任何一条业务行**（伤害、数值、音效、条件）出现在差异里。
这是本轮唯一的放行标准，见 §4.1。

## 4. 验收

### 4.1 parity 差异逐行核对（盖章前的审计）

重盖前 `node scripts/check-parity.js --rebase --verbose` 的输出：**移除 3 行 / 新增 36 行**。

移除的 3 行，每一行都有明确对应：

| 移除 | 去向 |
|---|---|
| `if(v.nightHint > 0) v.nightHint -= dt;` | 改写为 `world.visual.nightHint`（`v` 不再在编排层声明） |
| `if(world.evIdx >= … && t > 0){` | 其中 `t` 改为 `world.t`（等价：本帧内 `world.t` 不再变化） |
| `return;` | 变成 `stepZombies` 的 `return true` + 编排处的 `return` |

新增的 36 行全部是结构件：8 个函数声明、8 个收尾 `}`、7 个调用、1 个 `if(stepZombies…) return;`、
2 个 `return true/false`、2 个 `const t`、6 个 `const v`、2 行被改写的条件。

**关键结论：差异里没有任何一条业务行。** 伤害数值、音效名、开火间隔、状态迁移条件全部原样保留。

### 4.2 测试与轨迹

| 项 | 结果 |
|---|---|
| `npm test`（测试文件**零改动**） | **168 / 168** |
| 5 条绘制轨迹基线（**零更新**） | **全部逐字节一致** |
| `npm run verify` | **exit 0** |
| `parity` | 3437 / 3437（重盖后） |
| `fingerprint` | 39 / 39，变化 1 个文件（`src/core/sim.js`） |
| `dist` | 171.8 KB，戳 `· src` 摘要已随源码更新 |

**轨迹零更新这一条是最强的证据**：轨迹记录的是真实产物每一帧的 Canvas 调用与参数。若拆分的顺序、
随机数消耗或中断语义有任何偏移，僵尸位置与粒子分布就会不同，5 条基线不可能全部保持字节一致。

### 4.3 规模变化

| 指标 | 拆分前 | 拆分后 |
|---|---|---|
| `updatePlay` | 343 行 | **14 行** |
| `src/core/` 最大函数 | 343 行 | **109 行**（`stepPlants`） |
| `src/` 函数总数 | 117 | 125（+8 个 `step*`） |
| `src/core` 总行数 | 976 | 1015 |

函数总数与行数都增加了 3%~4%——这是拆分的正常成本，换来的是"改一条规则只需要进 15~110 行"。

### 4.4 本轮用到了上一轮的工具

重盖走的是 E1 新加闸的命令：`npm run parity:rebase` 与 `npm run fingerprint:update`
**各自先跑了 5 秒的 `npm test`**，全绿之后才写基线。这正是 E1 D4 想要的行为——
盖章之前先证明当前代码是绿的。

## 5. 遗留

- `stepPlants`（109 行）仍是 `src/core` 里最大的函数。它内部是一个 13 个 case 的 `switch`，
  继续拆的价值低于成本（每个 case 都需要 `world` + `p` + `dt` + `t`），本轮到此为止。
- 渲染层的两个大函数（`drawZombieEntity` 309、`paintBattleBG` 221）留给 E4。
- 护栏减负（5 条轨迹 → 2 条、fingerprint 扩范围）留给 E2/E5，且现在多了一条理由：
  本轮"轨迹零更新"证明了这 5 条轨迹确实能抓住 `src/core` 的行为漂移，删之前要想清楚。
