# 护栏评估 · parity 与 legacy 的去留（E8）

> 日期：2026-11-20
> 上游依据：[docs/项目分析-2026-11-20.md](项目分析-2026-11-20.md) §7 & §9 P1-7「护栏减负」。
> 本文是**评估与结论**，不是执行计划——结论是「两样都留」，理由见下。

## 1. 需要回答的问题

分析报告当时建议：5 条绘制轨迹砍到 2 条、fingerprint 扩范围、评估 `parity` 行快照是否还有价值。
E1–E7 做完之后，这个建议需要按**实测**重算，而不是按当时的估计。

## 2. 实测：护栏的成本与收益

| 机制 | 行数 | 何时需要重盖 | E1–E7 期间实际重盖次数 | 抓到过什么 |
|---|---:|---|---:|---|
| `parity` 快照 | 3,499 | 任何 `src/**` 改动 | 3（E3/E4/E5/E7 中 4 轮里有 4 次，其中 E6 无 src 改动） | 无（它是审计工具，不是拦截器） |
| `fingerprint` 源码 | 39 | 任何 `src/**` 改动 | 4 | 无 |
| `fingerprint` 工具 | 7 | 任何 `scripts/**` 改动 | 1 | **1 次**（E6 的篡改验证） |
| 浏览器轨迹 ×5 | 18,286 | **只有**有意改画面时 | **0** | 无（三轮重构证明"零更新即等价"） |
| 背景轨迹 ×2（E7 新增） | 6,401 | 只有有意改背景时 | 0 | 无 |
| 合计 | **28,232** | | | |

对比接手时：封条 21,729 行 / 源码 4,008 行 = 5.4 : 1。
现在：封条 28,232 行 / 源码 4,132 行 = **6.8 : 1**。

**护栏没有变少，反而变多了 27%。** 这不是失败，是发现了两个原本不存在的洞（E6 工具自指纹、E7 背景无防护），
但也说明"减负"这个方向的判断需要修正。

## 3. 逐条结论

### 3.1 parity 行快照：保留，但角色要改写

**它不是护栏，是审计工具。** E3/E4/E5/E7 四轮里，我每次都靠
`node scripts/check-parity.js --rebase --verbose` 得到"移除了哪几行、新增了哪几行"，
再逐行确认「没有一条业务行被改」。这件事 `fingerprint` 做不到——它只会说"文件变了"。

| | parity | fingerprint |
|---|---|---|
| 回答 | 哪些**行**变了（可读） | 哪些**字节**变了（不可读） |
| 强度 | 弱（不保序、过滤 import） | 强（任何字节） |
| 用途 | 盖章前的**人工审计** | 盖章的**触发器** |

两者不是重复，是"看"与"拦"的分工。**建议：保留，并在 README 里把它的定位从「基线」改成「改动审计」。**
真正的减负空间在于"每次改 src 都要重盖"这件事，而它和 fingerprint 是同一个代价，删掉 parity 也省不下来。

### 3.2 浏览器轨迹：保留 5 条，已确认不构成负担

三轮重构里有三轮是**零更新**通过的。成本只在"有意改画面"时兑现，而那时本来就要重看画面。
分析报告里"9 个文件要重盖"的估计，前提是"每次改代码都要重盖"，这个前提是错的。

### 3.3 `parity:legacy`：保留，但它是个博物馆

它冻结在 P3c、按设计就是非绿、不在 `verify` 里，还要带 tag 的完整检出。作为"护栏"它是零价值的。

但删除的代价是失去一件事：**"这次重构有没有改变行为"的最终取证能力**。
tag `pre-refactor-baseline` 里那个手写单文件是 R0–R6 十轮重构的起点，删掉工具之后，
要用它就得手敲 `git show` + 自己写比较脚本。

结论：**保留**，因为它现在不占日常成本（不在 verify 里、不参与任何绿灯判断），
只在需要考古时花几秒钟。但应当把它从"命令表"里降级到"考古附录"，避免被误当成日常工具。

### 3.4 真正该减的：背景轨迹的重盖入口（已修）

E7 新增的背景轨迹用 `UPDATE_BG_TRACE=1` 直接覆盖基线，**没有任何提示**。
这是当前唯一一个"静默吸收差异"的入口。

**已修**：重盖前先打印「原 N 行 / 新 M 行 / 行数差 / 首个差异在第几行及前后内容」，
与 `parity` / `fingerprint` 的 dry-run 对齐。不改成 `--yes` 二次确认，原因见下：

`npm test` 本身就包含这条背景轨迹测试。若照搬「先跑 `npm test` 再盖章」，
画面有意改动时 `npm test` 必然先红，盖章命令永远走不到——这条自我指涉的闸会把更新路径锁死。
因此这里保留"显式设环境变量即确认"的语义，但补上吸收量提示。

## 4. 结论

1. **不删 parity**，改写其定位为"改动审计工具"。
2. **不删 5 条浏览器轨迹**（已有三轮零更新的证据）。
3. **不删 `parity:legacy`**，但降级为考古附录。
4. **要修的**：背景轨迹的重盖门槛，与 E1 D4 对齐。
5. **对"护栏减负"这个建议本身**：按实测撤回。真实的问题不是护栏太多，而是**覆盖面不全**
   （工具、背景两处洞已由 E6/E7 补上），以及**一个重盖入口没有闸**（第 4 条）。

## 5. 一句话

**减负的反面不一定是不作为——这次是发现护栏该往哪儿加，而不是该往哪儿减。**
