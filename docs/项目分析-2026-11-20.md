## 1. 结论先行

**这是一个工程质量明显高于"同人小游戏"这个标签的项目。** 它真正的产物不是那个 171 KB 的 HTML，而是**一套把"纯前端单文件交付"和"可验证的模块化开发"同时成立的工程方法**——以及围绕它建立的、有点过度的护栏体系。

实测（本次运行，全部通过）：

| 命令 | 结果 | 耗时 |
|---|---|---|
| `npm test` | 165 个用例 / 24 个文件，0 fail | 4.8s |
| `npm run parity` | 3404 行快照逐行一致 | <1s |
| `npm run fingerprint` | 39 个源文件 SHA-256 一致 | <1s |
| `npm run test:smoke` | A–I 冒烟 ALL TESTS PASSED | ~2s |
| `npm run parity:dist` | 产物内联脚本与源码 bundle 逐字节一致（167.9 KB） | ~1s |
| `npm run test:browser` | 7 条（2 冒烟 + 5 绘制轨迹）全过，Playwright + 真实 dist | 26s |

三条主要判断：

1. **架构方向是对的**，不是"把代码搬进多个文件"的假模块化：依赖方向单向（`core` ← `render`/`ui`/`game`），副作用全部经端口注入，渲染对 `world` 严格只读。
2. **技术债是局部的、可定位的**，集中在少数几个巨型函数（`updatePlay` 343 行、`drawZombieEntity` 309 行、`paintBattleBG` 221 行）和渲染层的重复代码上，不涉及结构性错误。
3. **最值得讨论的不是代码，是护栏。** 目前"封条"（3404 + 18286 + 39 ≈ 21,700 行）是源码（约 4,000 行）的 **5.4 倍**，而其中至少三处在执行链上并不能证明它们声称要证明的东西。

## 3. 架构

### 3.1 分层与依赖方向

```
             main.js（装配：唯一知道浏览器的地方）
                │  注入 seed / ports / canvas / rAF
                ▼
   game.js ── 主循环 + dispatch(action)
     │
     ├─► core/    纯逻辑，不 import render/ui，不碰 DOM
     │     world.js    世界工厂（实例化，非单例）
     │     sim.js      一帧模拟 updatePlay
     │     actions.js  显式动作入口，统一返回 {ok, reason}
     │     entities.js 种植/出怪/伤害/小推车
     │     waves.js  quiz.js  particles.js  rng.js  util.js  data/*
     │
     ├─► ui/      界面状态（mouse/hoverCell/sel/shovel/hotspots）
     │
     └─► render/  只读绘制，仅经 addHotspot 回写交互语义
           target.js（ctx live binding）scenes/* 实体绘制
```

**方向被显式守住**：`src/core/` 里没有任何 `import ... from '../render/'` 或 `'../ui/'`；`core/world.js:1-5` 的注释把这条约束写成契约。`tests/render-boundaries.test.mjs` 与 `live-binding.test.mjs` 在测这条边界本身。

### 3.2 数据流

每帧在 `game.js:54-63`：
```
rAF → dt（上限 0.05s）→ frameState.t += dt
    → updatePlay(world, dt)   // 只在 play 且未暂停
    → render(world, ui, frameState)
```
渲染读 `world` 的 `state/level/t/sun/slots/plants/zombies/peas/suns/mowers/visual.*` 与 `ui` 的 `mouse/hoverCell/sel/shovel`；实测渲染前后 **world 的 JSON 完全一致**，唯一回写是 `ui.hotspots`（`render/scenes/index.js:15` 清空，8 处 `addHotspot` 注册）。

这是本项目一个很聪明的取舍：**渲染顺序即交互语义**（`ui/hotspots.js:12-18` 从后往前扫，后画的按钮压住先画的卡片），把"视觉层级"和"点击层级"绑成同一件事，避免了另一套布局表漂移。代价是渲染函数天然承担副作用，`render-readonly` 测试只能覆盖实体绘制，覆盖不到热点。

### 3.3 三个关键设计决策

**① 双随机流（R2a）** — `core/world.js:18-19`
```
rng    = mulberry32(seed)              // 战斗：出怪、速度、射击概率、阳光时刻
fxRng  = mulberry32(seed ^ FX_SEED_XOR)  // 表现：粒子、抖动、呻吟节奏
drawRng= mulberry32(seed ^ DRAW_SEED_XOR) // 绘制：震屏偏移
```
这是全项目最见功力的一处：`util.js:1-2` 明确注释"**这里不提供默认随机源——默认值会让'以为分流了、其实还在走全局源'悄悄通过**"。粒子的多少、帧率的高低不会反过来改变战斗结果。`tests/random-streams.test.mjs`（8 条）专门守这条不变量。

**② 端口注入（R2b）** — `core/ports.js`
`core` 只发同步调用 `sound()` / `saveProgress()` / `saveUnlockAll()`，默认实现全空。装配层在 `main.js:18-22` 注入真实实现。因此核心逻辑可以在 Node 里无浏览器跑完整对局——这是 165 条测试能成立的前提。

**③ 显式动作入口（R3）** — `core/actions.js`
所有交互统一成 `useCard / pickSlot / pressCell / collectSun / chooseLevel / togglePause / ...`，一律返回 `{ ok, reason }`，并承诺"失败不得部分扣费、推进冷却或改变目标"。`inspectUseCard`（`actions.js:16-30`）被**提交路径和悬停高亮共用**（`render/scenes/play.js:48`），所以"看起来能种"和"真的能种"由同一段代码决定——这个设计消除了一整类 UI/规则不一致的 bug。

## 4. 领域模型

```
world.state: menu ─┬─► help
                   ├─► select ──► quiz ──► play ──┬─► won
                   └──────────────────────────────┘   └─► lost
```

- **关卡**：4 关，`data/levels.js`——`count`（僵尸总数）、`slots`（可带卡数 6→8）、`types`（[类型, 权重]）、`night`。第 3 关起是 8 卡位。
- **植物** 13 种（`data/plants.js`）：`cost / hp / cool / mushroom / life`。特色机制齐全——蘑菇白天 `asleep`（需咖啡豆唤醒）、火炬点燃豌豆、土豆雷 14s 武装、迪迦限时 25s 贯穿光线。
- **僵尸** 6 种（`data/zombies.js`）：`hp + acc`（护盾）双血条，`damageZombie` 先吃 `acc` 再溢出到 `hp`（`entities.js:94-100`）。报纸僵尸护盾破后暴怒提速，是唯一带状态转换的敌人。
- **波次**（`waves.js`）：前 26 秒缓冲、前 3 只固定普通、间隔随进度收紧、末段 33% 的怪作为"一大波"集中投放。
- **经济**：阳光 50 起，夜战 +100 补偿；战前算数热身答对 1 题 ×2 能量（3 题全对 50×2³ = 400）。

一处值得记的小设计：`entities.js:119-124` `spawnZombie` 避免同一行连续三只，是纯粹的体验修正，却写在了规则层——位置合理。

## 5. 代码质量体检

### 5.1 做得好的

- **命名与注释密度**恰到好处：`sim.js:164-166` 解释"光线为什么只在本帧扫过僵尸前沿结算"这类非显然决策；`rng.js:5` 解释派生常量为什么写死。注释解释**为什么**，不复述**做什么**。

## 6. 交付与构建

```
src/main.js ──esbuild(bundle, iife, es2019, utf8)──► 单段 IIFE
            ──escapeForInline（</script、U+2028/29）──► assertCompiles(new Function)
            ──注入 shell.html 的 __BUNDLE__ ──────────► assertOffline（禁 src/href/网络 API）
            ──► dist/植物大战僵尸-网页版.html（+ 构建戳）
```

这套管线的克制之处：

- `scripts/esbuild-opts.js` 是**唯一**配置来源，build/dev/check-parity 共用——注释直说"否则 parity 两侧格式化规则不一致，会产生假红或假绿"。
- `inline.js:16-50` 的三道断言（语法可编译、无外部引用、无联网调用）把"离线自包含"这个唯一硬承诺变成了构建期失败，而不是文档里的口号。
- **pretty 是发布产物，min 只做等价验证**且被 `.gitignore` 排除——避免"提交哪个版本"的歧义。
- `--minify` 写 `.min.html` 不覆盖发布产物，这个细节避免了"验证构建污染交付物"的经典事故。

一个真实的运维风险：`npm run dev` **会覆盖发布产物**并写入 `/* dev build */`。缓解措施是浏览器套件断言首部必须是发布戳（`tests/browser/lib.mjs:19-28`），dev 产物冒充发布页会直接判红。这个设计是对的，但依赖"提交前跑过 browser 套件"。

## 7. 测试与护栏体系（本次分析的重点）

### 7.1 真实价值排序

**A 级——真正的保障**（约 130 条，建议长期保留）
- `sim-invariants`（12）、`world-isolation`（8）、`random-streams`（8）、`actions`（14）、`ports`（7）、`game`（13）、`input`（9）
- 7 个 `scenario-*`（40 条）：用**真实 core + 真实 render + 手动时钟**跑完整玩法，A–I 场景已从旧冒烟迁过来，并用 `killed === total` 这种强不变量守住波次守恒（[tests/scenario-outcome.test.mjs:86-100](../tests/scenario-outcome.test.mjs#L86-L100)）
- `render-readonly`（3）：序列化前后比对，证明绘制不改实体
- `helpers/scenario.mjs` 的 ctx 白名单（[tests/helpers/scenario.mjs:37-39](../tests/helpers/scenario.mjs#L37-L39)）——**新增绘制 API 不登记就抛错**，逼着改画面的人显式面对这层契约。这条比很多"覆盖率"都有用。

**B 级——有独立价值**：浏览器 release-smoke 2 条（真产物、真触屏、零外部请求断言）、`render-background`。

**C 级——可移植证据，但保证范围被高估**：parity 行快照、fingerprint、5 条绘制轨迹、`parity:legacy`、`live-binding`。

### 7.2 四道封条各能证明什么

| 机制 | 实际证明 | 不能证明 |
|---|---|---|
| **parity**（3404 行，去注释/折叠空白/剥 export/排序后比行多重集） | 行内容的增删 | 语句顺序、代码是否还在原函数、import 关系、文件边界、字符串内空白 |
| **fingerprint**（`src/**` 39 文件原始字节 SHA-256） | 有没有未登记的字节变化 | 变化是否正确；且**只覆盖 `src/`** |
| **绘制轨迹**（5 场景，Canvas 调用逐条比对，18,286 行） | 单帧的坐标/顺序/配色漂移 | 像素；背景缓存只记 `drawImage([object])`；单帧 |
| **构建戳** | 产物是 build 产物而非 dev 产物 | 产物是否**最新**（无 git SHA / 源码哈希） |

项目自己在 [docs/重构方案-v0.2.md](重构方案-v0.2.md) §3.1 就写了「**决策建议：保留搬迁对照价值，撤回行为等价承诺。**」——这个自我认知很难得。问题是：**文档里收回了承诺，执行链里还没收。**

### 7.3 执行链上的三个硬伤

1. **`verify` 顺序让 `parity:dist` 变成自证。**
   `package.json:21` 是 `parity → fingerprint → test → build → parity:dist → smoke → browser`。`build` 刚重写完 dist，紧接着 `parity:dist` 比对的当然是刚构建的结果。它**不能**证明"提交在仓库里的那份 dist 是最新的"。
   修法很便宜：把 `parity:dist` 挪到 `build` 之前，或加一步 `git diff --exit-code dist`。

2. **封条可在测试为红时一键重盖。**
   `--rebase` / `--update` / `UPDATE_TRACE=1` 都是一条命令直接写基线，没有"测试先绿"、没有 diff 确认、没有 `--yes`。历史上这不是理论风险：R3 重盖 99/233 行、R4 197/215 行（[docs/测试基线.md](测试基线.md)）。绿只代表"和上次盖章一致"。

3. **指纹覆盖范围与"严格源码指纹"的名字不符。**
   只走 `src/`（[scripts/check-fingerprint.js:27](../scripts/check-fingerprint.js#L27)）。改 `scripts/`、`tests/`、`package.json`、`headless_test.js` 都不触发。也就是说**护栏本身没有护栏。**

### 7.4 成本

| 改动类型 | 需要重盖的文件数 |
|---|---|
| 改一行逻辑 | 3（parity 快照 + fingerprint + dist） |
| 改任何绘制 | 3 + 6（5 条 trace + `baselines/env.json`）= **9** |
| 改注释/空白 | 1（fingerprint） |
| 改 tests/scripts | **0** ← 反直觉 |

改动绘制时，18,286 行基线里有意义的差异可能只有几行——[docs/测试基线.md](测试基线.md) 记录过 F1 轮"归一化后 0 行差异、只是渐变编号被顶偏"的情况。

### 7.5 一个值得注意的数字

**封条 21,729 行 : 源码 4,008 行 = 5.4 : 1。**

这个比例本身不是错——它换来了"重构不改变行为"这个极强的保证，也在 R0–R6 的十轮重构里真的防住了回退。但它是**一次性迁移期**的工具，而项目已经进入功能期（F1 加了一种植物）。迁移期该严，功能期该快，工具没跟着换挡。
